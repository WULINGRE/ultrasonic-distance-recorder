# ST7735 屏 ASCII 字符显示异常分析

分析对象：`Hardware/font.c`、`Hardware/font.h`
显示驱动：`Hardware/st7735.c` 的 `LCD_ShowChar()` / `LCD_ShowStringUTF8()`

---

## 0. 结论速览

| 现象 | 根本原因 |
|---|---|
| 字母对不齐、字距忽大忽小 | `font.c` 里是一套**比例字体（每字宽窄不同，最窄 1 px、最宽 8 px）**，而 `LCD_ShowChar()` 固定按 **8 像素** 步进。字宽差 + 居中空白差，直接变成看得见的"错位"。 |
| 大小不一 | 每个字形的墨迹高度在 **9 ~ 13 px** 之间浮动，起止行也不统一（row 2 / 3 / 5 起笔，row 12 / 13 / 14 收笔）。 |
| 粗细不同 | 笔画宽度混用 1 px 和 2 px；单位墨迹量从 6 px（`i`）到 22 px（`m`），相差 3.5 倍。 |
| 个别字母形状怪（`J`、`?`） | 这些字模带明显的 **点阵中文字库风格**（竖笔落在最右列、带中文字形钩笔），与本套拉丁字重、风格不一致。 |

**位序没有问题**：`font.c` 数据是 MSB-first（bit7 = 最左像素），`font.h` 的注释、`st7735.c` 的 `0x80 >> col`、以及 `Font_GetASCII8x16()` 的下标换算三者完全一致。字符方向没有镜像、没有逐列错位。

---

## 1. 数据格式与方向校验（先排除经典嫌疑）

`font.c` 采用**逐行**存储（1 行 = 1 字节，共 16 字节），这一点和常见的"列行式"字库不同，容易踩坑，但这里是对的：

```c
/* st7735.c:293,298 */
data = ASCII8x16[index][row];                 // row 0..15 逐行取
pixel = (data & (0x80 >> col)) ? color : bgcolor;   // bit7 -> 最左
```

用 `j`（唯一带下伸到 row 14 的 ASCII 字符）反推验证：

```
0x6A 'j' = { 0x00,0x08,0x00,0x00,0x00,0x38,0x08,...,0x08,0x18,0x70,0x00 }
row1 = 0x08 -> 00001000  点
row5 = 0x38 -> 00111000  横
row14= 0x70 -> 01110000  左下钩
```

点在上、横在中、钩在左下 —— 只有 MSB-first 才成立。若按 LSB-first 解释，`J`、`U`、`L`、`W` 会全部左右镜像。**所以问题 100% 在字模数据本身，写数据的那段代码是无辜的。**

> 顺带提醒：`Hardware/OLED_Font.h` 的 `OLED_F8x16` 是**列行式 + LSB 在上**（列优先，每列 1 字节，bit0 是最上面的像素），和 `font.c` 的格式**完全不同**。两套字库不能互相拷贝，拷过来会变成一堆竖条纹。

---

## 2. 根因一：比例字体被塞进等宽格子（"对不齐"的主因）

把 95 个字形逐一解码，量出各自的墨迹列范围：

| 字符 | 墨迹列 | 墨迹宽 | 左空白 | 右空白 |
|---|---|---|---|---|
| `i` `l` | 2..4 | 3 | 2 | 3 |
| `!` `\|` | 3..4 | 2 | 3 | 3 |
| `j` `r` `t` | 3..5 | 3 | 3 | 2 |
| `c` `f` `s` `z` `I` `1` | 2..6 | 5 | 2 | 1 |
| `J` | 2..7 | 6 | 2 | 0 |
| `M` `m` `w` `T` `_` | 0..7 | 8 | 0 | 0 |

而驱动是**无条件 +8**：

```c
/* st7735.c:418,438 */
width = (unicode <= 0x7F ? 8U : 16U) * size;
...
x += width;
```

### 用 `"POWERED BY"` 算一遍（这是屏上真实显示的内容，main.c:54）

每个字符占 8 px，墨迹落点如下：

```
字符  占位区间   墨迹区间    左边距  右边距
 P     0..7      1..6  (6)     1       1
 O     8..15     9..14 (6)     1       1
 W    16..23    16..22 (7)     0       1
 E    24..31    25..30 (6)     1       1
 R    32..39    33..38 (6)     1       1
 E    40..47    41..46 (6)     1       1
 D    48..55    49..54 (6)     1       1
(空)  56..63     —             8       8
 B    64..71    65..70 (6)     1       1
 Y    72..79    73..78 (6)     1       1
```

相邻字符的**实际墨迹间隙**：

```
P-O:1   O-W:2   W-E:3   E-R:3   R-E:3   E-D:3   D-␣:9   ␣-B:9   B-Y:3
```

`1、2、3、9` 四种间隙随机出现 —— 这就是看到的"对不齐"。

同一句话里 `W`（7 px 墨宽）和 `I`、`1`（5 px）和 `i`、`l`（3 px）挤在同一个 8 px 步进里，**每行字符串的横向节奏完全乱掉**。`main.c:56` 的 `"STM32F103C8T6"` 更极端：`I` 只有 5 px 宽，`M`、`T` 有 8 px 宽，`1` 的左右边距还不对称（左 2 右 1）。

## 3. 根因二：垂直基线不统一（"大小不一"的主因）

统计全部 95 个字形：

```
墨迹高度分布 : 1px×4, 2px×6, 3px×5, 5px×7, 7px×1, 8px×12, 9px×2, 10px×33, 11px×11, 12px×6, 13px×6, 14px×1
起始行分布   : row2 ×15, row3 ×49, row4 ×1, row5 ×11, row6 ×1, row7 ×5, row8 ×2, row11 ×1
结束行分布   : row7 ×1, row8 ×2, row11 ×1, row12 ×60, row13 ×11, row14 ×1, row15 ×6
```

- **x-height 字形**（`a c e m n o r s u v w x z`）从 row 7 起笔、到 row 12 收笔 → 高 6 px
- **cap height 字形**（`A B D E H I K L M N P R T U V W X Y Z`、`1`~`9`）从 row 3 起笔、到 row 12 收笔 → 高 10 px
- **上伸部**（`b d f h k l t`）从 row 2 起笔 → 高 11 px
- **下伸部**（`g j p q y`）到 row 14 收笔 → 高 13 ~ 14 px
- **越界字符**：`$`（底行 row 12）与 `(` `)` `[` `]` `{` `}` `/` `\` 和 `j` 到 **row 15**，也就是**顶到 16×16 格子的最底边**

也就是说：**同一个 16 px 高的格子里，有的字占 6 px、有的占 14 px，起笔位置还差 4 行。**

对比 `st7735.c` 里画中文的部分，中文是统一 16×16 满格的；ASCII 只有 10 px 高、还浮在中间 —— 所以一行中英文混排时（`main.c:52` 的 `"Hello, 超声波!"`），英文字母看起来"小一号、还往上/往下飘"。

## 4. 根因三：笔画粗细混用（"粗细不同"的主因）

按每个字形点亮的像素总数排：

| 字形 | 墨迹像素数 | 笔画宽度 |
|---|---|---|
| `i` `l` `!` | 6 ~ 8 | 1 px |
| `j` `r` `t` | 9 ~ 11 | 1 px |
| `c` `s` `z` | 11 ~ 13 | 1 px |
| `a e o u v x` | 15 ~ 19 | 2 px |
| `0 6 8 9 O Q` | 18 ~ 21 | 2 px |
| `m` | 21 | 3 px 横 |
| `W` `M` | 22 | 2 px 斜 |
| `_` | 8 | 1 px（横跨 8 列） |

`i`（6 px 墨迹）和 `m`（21 px 墨迹）在屏幕上挨着出现时，视觉重量差 3.5 倍 —— 这就是"粗细不同"。

具体到字符级的不一致（解码确认）：

- **`1` 的斜头只有 1 px 宽**，而 `0`、`6`、`8`、`9` 的曲线都是 2 px 宽 → `1` 明显偏细
- **`2` 的斜笔只有 1 px 宽**（`0x06 → 0x0C → 0x18 → 0x30`，阶梯式），同样偏细
- **`T` 的竖笔只有 1 px 宽**（`0x18`），顶横却是满 8 px（`0xFF`）→ 头重脚轻
- **`i` 的圆点是 2×2**（row2~3, x3~4），而 `.` 是 1×1、`:` 是 2×2×2 → 同类点的尺寸不统一

## 5. 根因四：个别字形来自另一套风格（"个别字母怪"）

`J` 解码结果：

```
row3  00111000  x2-x5
row10 11001100  x0-x1 + x6-x7   <-- 竖笔跑到了最右列 x7
row11 01111000  x1-x4
row12 00000000
```

问题：
1. 顶横在 x2~x5，竖笔在 x7，**钩脚在 x1~x4** —— 三者不在同一竖线上，整个字往右"歪"
2. row 10 的 `0xC0` 出现在 x0~x1，左边伸出去 2 px，是典型的中文字形"撇"的写法
3. 竖笔直接顶到最右列 x7，右边距 = 0

`?` 解码结果：

```
row3  00111100  x2-x5
row4  01100110  x1-x2 + x5-x6
row6  00001100  x4-x5
row7  00011000  x3-x4
row9  00011000  x3-x4   <-- 点和上面的竖笔连在一起了
row10 00011000  x3-x4
```

问题：问号的"点"（row9~10）和上面的竖笔（row7）**中间没有断开**，看起来像一根带弯的长杆，而不是问号。正常 8×16 点阵问号至少有 1 行空隙。

`Q` 同样异常：尾巴画在 row 11~12 的 **x2~x4 内部**（`0x0C,0x04`），而不是像 `@` 那样伸出到格子外，导致 `Q` 和 `O` 几乎分不出来。

这些痕迹说明：这套 ASCII 字模**不是从同一套拉丁点阵字库导出的**，至少 `J Q ? @ ` 等是从点阵中文字库/比例字体截图转出来的，字重和骨架都与 `A B C E H` 那一套不匹配。

## 6. 修复方案

### 方案 A（推荐，改动最小）：换一套真正的等宽 8×16 字模

保持 `LCD_ShowChar()` 的 `x += 8` 不变，把 `ASCII8x16` 换成一款**专为 8×16 等宽格子设计**的字体（例如经典 IBM VGA 8×16 / Fixedsys 风格）：

- 每个字形墨迹一律落在 **x1~x6**（左右各留 1 px），cap height 一律 **row 3 ~ row 12**
- 下伸部统一到 row 14，上伸部统一到 row 2
- 所有笔画统一 1 px（小字号等宽字体本来就该单像素）

这样字距、基线、字重会同时归位，且中文/英文混排时高度关系也自然。

### 方案 B：保留比例字体，改成真的比例排版

需要给字模加"步进宽度"表，并让驱动按实际宽度前进：

```c
/* font.h */
typedef struct {
    uint8_t width;              /* 该字符的步进宽度 1..8 */
    uint8_t data[FONT_ASCII_HEIGHT];
} AsciiGlyph;

extern const AsciiGlyph ASCII_Proportional[];

const AsciiGlyph *Font_GetASCII(char ch);
```

```c
/* st7735.c : LCD_ShowStringUTF8() 里 */
if (unicode <= 0x7F) {
    const AsciiGlyph *g = Font_GetASCII((char)unicode);
    width = g->width * size;             /* 按实际步进前进 */
    ...
    x += width;
}
```

`LCD_ShowChar()` 也要相应改成按 `g->width` 设置地址窗口，不能再写死 8。

方案 B 效果最接近你看到的"原设计意图"（字模本身是比例字体），但要同步改 `font.h`、`font.c`、`st7735.c` 三处，工作量比 A 大。

### 方案 C（临时缓解）：只增加字距，不动字模

在 `LCD_ShowChar()` 里把 `x += 8` 改成 `x += 9`，同时把字形地址窗口从 8 列缩到 7 列。这只能让字距均匀一点，**不能解决基线不统一和粗细不一**，属于治标。

## 7. 需要一并确认的点（不在本次范围内）

1. `LCD_MADCTL = 0xA8` + `LCD_X_OFFSET = 0` / `LCD_Y_OFFSET = 0` —— 若实际面板是 128×160 的 ST7735S，通常需要 `x_offset = 0, y_offset = 0` 或 `2/1`，方向设置不对会让整屏内容整体偏移，容易被误认成"字对不齐"。
2. `main.c:62` 的 `"mm"` 画在 `x = 64`，而 `main.c:60` 的 `"Distance:"` 从 `x = 0` 开始占 9 个字符 = 72 px，两者会**重叠**（`Distance:` 的墨迹到 x66，`mm` 从 x64 起笔）。这是坐标问题，不是字库问题。
